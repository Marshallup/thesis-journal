# Thesis — дизайн

> **Thesis** — дневник инвестиционных решений.
> *Записано до, а не после.*

Пет-проект под смену трека на бэкенд. Дневник решений и сделок по крипте и российскому фондовому рынку с рыночным пайплайном. Не тренажёр: Михаил реально покупает активы, поэтому данные и пользователь настоящие с первого дня.

Название отражает суть: продукт хранит не «что купил» (это показывает и брокер), а **тезис — почему, записанный до того, как стал известен исход** (§2.1). По-русски в разговоре — «Тезис». Родовое «Trade Journal» в имя сознательно не берём: оно врёт про горизонт (у нас инвестор, а не трейдер), противоречит фиче «решение без сделки» и делает имя неотличимым в поиске от десятка существующих журналов.

Рабочие имена: репозиторий `thesis-journal`, домен — см. «Открытые вопросы».

Связанные заметки: [[Профиль]], [[Сводки/Бэкенд]], [[СВОДКА]].

## Зачем этот проект

Проект даёт навыки только тогда, когда домен заставляет решать задачи, на которых валят на senior-собеседованиях. Тест из трёх вопросов:

- есть ли место, где двое одновременно меняют одно? — **да** (виртуальный кэш, условные ордера, конкурирующие воркеры);
- есть ли операция дольше секунды? — **да** (синхронизация с биржами, backfill свечей, парсинг отчётов);
- будет ли таблица на миллион строк? — **да, настоящих** (минутные свечи: год по 20 тикерам ≈ 10 млн записей).

Наивный дневник («купил 0.1 BTC, заметка») этот тест проваливает — это todo-приложение. Вся ценность в пайплайне вокруг журнала.

## 1. Границы сервисов и потоки данных

Монорепозиторий (pnpm workspaces): `apps/*` — сервисы, `packages/contracts` — типы событий и Zod-схемы, `packages/db` — Prisma-клиент и миграции. Один `docker-compose up` поднимает всё.

| Сервис | Отвечает за | Владеет таблицами |
|---|---|---|
| `api` | HTTP REST + OpenAPI, auth, WS-шлюз к браузеру | `users`, `accounts`, `api_keys`, `portfolios` |
| `ingestor` | коннекторы к биржам и брокеру, WS-подписка на цены, парсинг отчётов | `instruments`, `instrument_aliases`, `sync_cursors`, `raw_imports` |
| `core` | сделки, лоты FIFO, позиции, P&L, условные ордера, виртуальный кэш | `trades`, `decisions`, `decision_revisions`, `decision_trades`, `lots`, `lot_consumptions`, `positions`, `orders`, `cash_ledger`, `cash_balances` |
| `notifier` | алерты, доставка в Telegram, effectively-once | `alerts`, `deliveries` |

**Схема на сервис, инстанс PostgreSQL один.** Отдельные БД для соло-проекта — боль с миграциями без выгоды. Отдельные схемы дают ту же дисциплину «не лезь в чужие таблицы».

```
Bybit/Bitget WS ─┐
Т-Инвест gRPC ───┼─> ingestor ──Kafka: market.ticks (partition by symbol)──┬─> core (переоценка позиций)
Сбер XLSX ───────┘       │                                                 ├─> notifier (алерты)
                         │                                                 └─> marketdata-consumer ─> ClickHouse (свечи)
                         └──Kafka: trades.imported──> core ──Kafka: positions.changed──> api ──WS──> React
                                                                                          notifier
```

**Две очереди по назначению — сознательное решение:**

- **RabbitMQ — команды**: `sync-account`, `parse-report`, `backfill-candles`. Нужны ретраи, DLQ, ack после работы, rate limit.
- **Kafka — потоки событий**: тики (партиции по тикеру → порядок внутри тикера), `trades.imported`, `positions.changed`. Нужны consumer groups, офсеты, дедупликация.

Kafka как очередь задач — известный антипаттерн: ретрай одной задачи блокирует партицию. Ответ на собеседовании «почему не один брокер» будет из практики, а не из статьи.

**API-поверхность — две, с чёткой границей:**

- **REST + OpenAPI** — команды и мутации: импорт, синхронизация, создание решения, подключение ключей. Там, где важны идемпотентность, HTTP-семантика, ретраи и публичная спека.
- **GraphQL** (неделя 9) — только чтение дашборда и аналитики. Экран «Портфель» тянет пять разнородных кусков (позиции, последние сделки, срезы решений, активные алерты, метрики дня): это учебниковый случай против водопада REST-запросов и разрастающегося эндпоинта `/dashboard`.

По нужде GraphQL проекту не требуется — клиент один, данные табличные и агрегатные. Берётся ради рынка (26%, у Зерно-Агрегатора в ядре стека вместе с Nest и Prisma) и потому, что для одного экрана он объективно уместен. Два правила, чтобы он не съел глубину по SQL, ради которой всё затевалось: резолверы зовут **те же самые** запросы через общий слой репозиториев (генерировать свои GraphQL не может), и есть интеграционный тест на количество запросов, который падает при появлении N+1. Обязательны DataLoader, depth limit, complexity limit. Подписки остаются на своём WebSocket — `graphql-ws` не берём.

## 2. Модель данных

**Деньги — только `numeric`, никогда float.** `numeric(38,18)` для количеств (крипта до 18 знаков), `numeric(28,8)` для цен и сумм. Наружу — строками, внутри — `decimal.js`.

| Таблица | Суть | Что тренирует |
|---|---|---|
| `trades` | факт сделки, неизменяемый | `UNIQUE (account_id, provider, external_id)` — ключ идемпотентности импорта |
| `decisions` / `decision_trades` | решение «почему я это делаю» и его связь со сделками | append-only, ревизии, `jsonb`-снимок контекста — см. §2.1 |
| `lots` / `lot_consumptions` | открытые партии и их списание при продаже | FIFO, частичные продажи, реализованный P&L построчно |
| `positions` | агрегат по инструменту + `version int` | optimistic locking, lost update |
| `cash_balances` | остаток по валюте + `CHECK (amount >= 0)` | check-and-decrement под `FOR UPDATE`, инвариант в БД, а не в коде |
| `cash_ledger` | все движения денег, append-only | сверка «сумма ledger = баланс» |
| `orders` | условные ордера бумажного режима | гонка двух ордеров за один кэш |
| `fx_rates` | курсы ЦБ РФ | приведение P&L к базовой валюте по курсу **на дату сделки** |

Нереализованный P&L **не храним** — считается на лету из последней цены в Redis. Хранимый производный показатель, который может разъехаться с источником, — источник багов.

**Счета.** У `accounts` есть `base_currency`, `provider`, `kind` (`exchange` / `broker` / `manual` / `paper`) и флаг `is_iis` — у ИИС свой горизонт и налоговый режим.

**Tiered storage для рыночных данных.** Если все свечи уедут в ClickHouse, PostgreSQL останется на сотнях строк, и глубина по PG (89% рынка, главный гэп) улетучится. Поэтому:

- **PostgreSQL** — горячее окно: минутные свечи за 30 дней, партиции по неделям, автосоздание партиций по расписанию, `DROP PARTITION` вместо `DELETE`.
- **ClickHouse** — архив: `ReplacingMergeTree ORDER BY (symbol, tf, ts) PARTITION BY toYYYYMM(ts)`, годы истории.
- Один и тот же запрос «портфель по дням за год» пишется под оба и сравнивается через `EXPLAIN ANALYZE` → `docs/benchmarks.md`.

Это единственное сознательное дублирование данных в проекте, принято ради учебной ценности.

**Транзакционный outbox.** В каждой схеме — `outbox_events`: событие пишется в БД в той же транзакции, что и бизнес-изменение, отдельный relay публикует в Kafka. На стороне консьюмеров — `processed_messages` для дедупликации.

## 2.1. Дневник решений — почему, а не только что

Ключевая фича продукта, а не дополнение. P&L показывает и приложение брокера; **лога решений нет ни у кого**. Без него и AI-глава (§8) пустая: поверх одних сделок LLM пересказывает таблицу, которую ты и так видишь.

**Сущность `decisions`, а не «комментарий к сделке»:**

- одно решение → 0..N сделок (`decision_trades`): докупка лесенкой в три захода — это одно решение, а не три;
- решение **может быть без сделки** — «хотел купить, не купил». Система сама посчитает, сколько принесло или стоило бездействие. Инфраструктурно бесплатно, а по ценности — то, чего не ведёт почти никто;
- запись **иммутабельна**, правки — новой ревизией (`decision_revisions`) с сохранением исходной. Иначе заметка перепишется под уже известный исход, и аналитика превратится в самообман. Заодно честная техническая деталь: append-only + аудит ревизий.

**Поля.** Структурированный минимум заполняется за 20 секунд: `thesis` (одна строка), `horizon`, `conviction` 1–5, `mood` (список), `invalidator` («что докажет, что я неправ»), теги. Свободный текст — сверху и по желанию. Пустое поле «комментарий» не работает: заполняется пять раз, потом забрасывается. `invalidator` — самое недооценённое поле: сделка без заранее записанного условия выхода держится дольше и закрывается хуже.

**`context_snapshot` (`jsonb`) заполняется автоматически**, без участия человека: цена, волатильность, время суток и день недели, просадка портфеля на этот момент, число сделок за последние 24 часа. Половина будущей аналитики берётся отсюда даром. Тип намеренно `jsonb` — новые источники контекста добавляются без миграции (см. роадмап).

**`outcome` считается сам** при закрытии позиции: реализованный P&L по привязанным лотам, время удержания, максимальная просадка внутри сделки.

**Матчинг решения и сделки.** Решение записывается **до** сделки, а сама сделка приезжает из импорта часом или днём позже — поэтому связь не задаётся руками при вводе, а подбирается:

- кандидаты ищутся по счёту, инструменту, направлению и временному окну `[created_at, created_at + horizon]`;
- автопривязка — только при однозначном совпадении; иначе сделка попадает в очередь «подтверди привязку» в UI;
- ручная привязка и отвязка доступны всегда — связь живёт в отдельной таблице и иммутабельности самого решения не нарушает;
- если сделки в горизонте так и не появилось, решение помечается несовершённым и уходит в учёт бездействия.

Это единственная по-настоящему нетривиальная часть фичи: сопоставление асинхронно приезжающих данных с уже записанным намерением.

**Ценность приходит тремя уровнями, и LLM — только третий:** уровень 0 — перечитать собственный тезис через три месяца (работает сразу, без аналитики); уровень 1 — SQL-срезы, то есть обычные `GROUP BY` (примерно 80% аналитической пользы); уровень 2 — LLM формулирует словами и разбирает свободный текст. Поэтому фича делается на 2-й неделе, а не вместе с AI-главой: ждать LLM значит прийти к ней с пустым корпусом записей.

**Разделение труда: SQL считает, LLM формулирует.** Поведенческие срезы — обычные агрегаты: уверенность против результата, сделки в день просадки портфеля, сделки без `invalidator`, «больше трёх сделок за сутки». LLM получает уже посчитанные числа и пишет разбор словами. Позволить модели считать самой — получить уверенные галлюцинации про собственные деньги.

**Три ограничения, зашитые в дизайн:**

1. **Порог значимости.** Десятки сделок в год — это не статистика. В каждом срезе показывается `n`; при `n < 20` вывод не формулируется вовсе, только «данных пока мало». Зашито и в UI, и в промпт. Без этого фича вредна: уверенный вывод по 12 наблюдениям меняет поведение с реальными деньгами.
2. **Приватность.** Настроение и личные записи — чувствительные данные, а регистрация публичная. Заметки не попадают в демо-аккаунт никогда; отправка во внешний LLM — только по отдельному явному согласию, с альтернативой в виде локальной модели (Ollama); текст шифруется тем же механизмом, что и ключи бирж (§5).
3. **Тон.** Формулировки отчётов нейтральные, про закономерности. Дневник не должен превращаться в инструмент самобичевания.

**Дисциплина заполнения.** Батч-разметка неразмеченных сделок списком + напоминание в Telegram «появились сделки без тезиса» (неделя 8, когда есть `notifier`). Без этого фича тихо умирает — это главный риск, и он не технический.

## 3. Конкурентное ядро

| Сценарий | Приём | Как ломаем в тесте |
|---|---|---|
| Повторная синхронизация тянет те же сделки | `INSERT … ON CONFLICT (account_id, provider, external_id) DO NOTHING` | прогнать sync дважды, сверить `count(*)` |
| Двойной клик «Синхронизировать» / крон совпал с ручным запуском | `pg_advisory_xact_lock(account_id)`, второй запуск выходит сразу | два HTTP-запроса в один момент |
| Один и тот же отчёт залит дважды | `UNIQUE (account_id, file_hash)` в `raw_imports` | залить файл повторно |
| Две покупки на один и тот же виртуальный кэш | `UPDATE cash_balances SET amount = amount - $1 WHERE account_id = $2 AND amount >= $1 RETURNING` + `CHECK (amount >= 0)` | два параллельных запроса, успешен ровно один |
| Два условных ордера сработали от одного тика, кэша хватает на один | одна транзакция, `FOR UPDATE` на балансе, порядок `ORDER BY created_at, id` | подать тик, пробивающий оба триггера |
| Два воркера обрабатывают один алерт | `SELECT … FOR UPDATE SKIP LOCKED LIMIT 1` + `UNIQUE (alert_id, triggered_at)` в `deliveries` | поднять 3 реплики `notifier` |
| Опоздавшая цена затирает свежую | upsert с монотонным гардом `WHERE excluded.ts > prices.ts` | подать тики в обратном порядке |
| Фоновый пересчёт + ручное редактирование сделки | `version`-колонка, `UPDATE … WHERE version = $1`, при 0 строк — ретрай | задержать пересчёт, отредактировать сделку |
| Консьюмер упал посреди батча | ручной commit офсета после записи + `processed_messages` | `docker kill` в середине обработки |

**Уровни изоляции.** Базовый режим `READ COMMITTED`; исполнение ордеров — `REPEATABLE READ` с отловом `40001 serialization_failure` и ретраем. Разница между «блокировкой» и «сериализацией» — на практике.

**Формулировка про доставку.** Kafka не даёт exactly-once в связке с внешней БД. У нас at-least-once + идемпотентный ключ записи = **effectively-once**. На собеседовании говорить именно так.

## 4. Коннекторы и импорт

Одна абстракция в `packages/contracts`, четыре намеренно разных по транспорту реализации:

```ts
interface TradeSource {
  fetchOperations(cursor: Cursor, window: TimeWindow): AsyncIterable<RawOperation>
}
interface PriceSource {
  subscribe(symbols: string[]): AsyncIterable<Tick>
}
```

| Провайдер | Транспорт | Подводные камни |
|---|---|---|
| Bybit | REST v5 `/v5/execution/list` + public WS | окна ≤ 7 дней, курсорная пагинация, retention ~2 года |
| Bitget | REST, своя пагинация и лимиты | ломает «абстракцию под один API» — и это полезно |
| Т-Инвестиции | Invest API, gRPC (+ sandbox) | другой протокол целиком, инструменты по FIGI/UID, стримы |
| Сбер ИИС | XLSX-отчёт вручную | парсинг, кривые колонки, ручная сверка |

**Сырьё сохраняем всегда.** Ответ провайдера или файл целиком ложится в `raw_imports`, и только потом нормализуется. Баг в маппинге чинится перегоном из сырья.

**Не всё, что приходит, — сделка.** У Т-Инвест в потоке операций идут дивиденды, купоны, комиссии, налог, пополнения. Сделки → `trades`, остальное → `cash_ledger`. Если свалить в кучу, P&L поедет.

**Rate limit — в Redis, а не в процессе.** Token bucket на провайдера, общий для всех реплик `ingestor`; локальный лимитер при трёх репликах даёт тройной трафик и бан. Сверху — exponential backoff с джиттером и circuit breaker на провайдера.

**Один инструмент — много алиасов.** `instrument_aliases (provider, provider_symbol) → instrument_id`, чтобы BTC на Bybit и BTC на Bitget сводились в одну строку портфеля. Времена — `timestamptz` в UTC; MOEX по Москве, крипта 24/7.

**Тесты коннекторов — на записанных фикстурах** (msw/nock) + sandbox Т-Инвест. Живые API из тестов не дёргаем.

## 5. Безопасность и мультиюзер

**Аутентификация.** Пароли — argon2id. Access-JWT 15 минут, refresh в httpOnly+Secure+SameSite cookie с ротацией и обнаружением переиспользования (повторно применённый refresh убивает всё семейство токенов). Логин под rate limit в Redis + прогрессивная задержка.

**Изоляция данных — два рубежа.** `user_id` из токена в каждом запросе + **Row Level Security** в PostgreSQL (`SET LOCAL app.user_id`) как страховка от одного забытого `WHERE user_id = …`.

**Ключи бирж.** AES-256-GCM, per-record nonce; мастер-ключ в файле на сервере с правами 600 — **не в БД и не в том же бэкапе**. Поле write-only: наружу только маска `bybi…7f3a`. При подключении валидируем права ключа и **отказываемся принимать ключ с правом на торговлю или вывод средств** — дневнику нужен read-only.

**Фича-флаг `exchange_keys`.** Регистрация открыта всем, подключение биржевых ключей — по allowlist (сначала только владелец). Остальным доступны ручной ввод, импорт CSV/XLSX, бумажный режим и публичные цены — продукт полноценный. Флаг снимается осознанно, а не по умолчанию.

**Бэкапы.** `pg_dump` по расписанию + выгрузка в S3-совместимое хранилище + ежемесячная проверка восстановления. Бэкап, который ни разу не разворачивали, — не бэкап.

**Прочее:** секреты в GitHub Actions secrets, маскирование ключей и токенов в логах, дисклеймер «не является инвестиционной рекомендацией», политика конфиденциальности.

## 6. Тесты, наблюдаемость, эксплуатация

- **Unit** — доменное ядро (FIFO, комиссии, P&L, конвертация валют) как чистые функции. Плюс **property-based** (fast-check) на инварианты: «сумма остатков лотов = количество в позиции», «сумма `cash_ledger` = баланс», «полная распродажа обнуляет позицию при любой последовательности сделок».
- **Интеграционные — на Testcontainers** (реальные PostgreSQL, Kafka, Redis, ClickHouse). Прямой гэп: unit senior, интеграционные — 58% рынка.
- **Гоночные** — отдельная категория: N параллельных запросов, успешен ровно один. Каждая строка таблицы §3 = один тест.
- **Контрактные** — Zod-схемы событий, версионирование с первого дня (`market.ticks.v1`).
- **E2E (Playwright)** — один сценарий: регистрация → импорт отчёта → верная сумма портфеля.

**CI (GitHub Actions):** lint → typecheck → unit → integration (Testcontainers) → сборка образов → деплой по тегу.

**Наблюдаемость.** Структурные логи (pino) с `correlation_id`, проходящим **через Kafka-заголовки**. OpenTelemetry-трейсы, Prometheus + Grafana. Дашборд: лаг consumer-групп, глубина очередей RabbitMQ, время и успешность синхронизации по провайдерам, доля 429, p95 API, **расхождение `cash_ledger` и `cash_balances`** (сверка раз в час — если разъехалось, конкурентность течёт). Алерты себе в Telegram через `notifier`.

**Эксплуатация.** Graceful shutdown обязателен (иначе дубли на каждом деплое), миграции expand/contract, health/readiness пробы, рестарт-политики.

**Генератор нагрузки** — отдельная утилита: заливает годы минутных свечей и поток тиков. Без неё `EXPLAIN ANALYZE` показывает «и так быстро».

## 7.1. Как ведём разработку

Проект учебный, поэтому метод работы — часть дизайна, а не личное дело.

**Исходный факт, от которого всё строится:** если ИИ пишет код, а Михаил его читает, обучения не происходит. Чтение понятного кода даёт иллюзию беглости — на собеседовании без подсказок не воспроизводится. Учит усилие извлечения (вспомнил и написал сам) и отладка собственных ошибок.

**Скелет процесса** (взято от spec-driven, без фреймворков): спека → план на 2–3 недели → задачи по 2–4 часа → одна задача = одна ветка = один PR в свой же репозиторий. Осмысленные описания PR — часть витрины.

**Три слоя кода:**

| Слой | Что | Режим |
|---|---|---|
| Пишет сам | SQL и миграции, транзакции и локи, конфиг Kafka-консьюмера, FIFO и P&L, гоночные тесты | ИИ только как справочник, код не просит |
| ИИ пишет, разбирает построчно | Nest-обвязка, DTO, контроллеры, React-компоненты, compose, CI | не мержит, пока не может объяснить каждую строку; в каждом куске переписывает минимум одну вещь по-своему |
| ИИ делает целиком | сиды, фикстуры, скрипты, стили, генератор нагрузки | читает по диагонали |

Первый слой — около 30% кода и 90% ценности проекта. В `CLAUDE.md` репозитория зафиксировано правило: **SQL и тесты ИИ за Михаила не пишет.**

**Размер куска:** задача ≤ 4 часов, ≤ ~300 строк диффа, заканчивается зелёными тестами и запускающимся приложением. Не влезает — это две задачи.

**Цикл на задачу:** прочитал кусок спеки → пересказал своими словами в двух предложениях → написал тест руками → написал код по слоям → **сломал специально** (сценарии из §3) → пять строк в `docs/learning.md` своими словами → PR с вопросом «что бы спросили на собеседовании по этому коду» и ответом.

**Проверка усвоения — три механики:**

1. **Воспроизведение по памяти.** Раз в неделю одна уже написанная вещь (запрос с `FOR UPDATE SKIP LOCKED`, конфиг консьюмера, миграция с партицией) пишется с нуля в пустом файле без подсказок. Расхождение с оригиналом = реальный уровень.
2. **Журнал незнания** (`docs/unknowns.md`) — что не понял и отложил; две-три позиции закрываются еженедельно.
3. **`docs/incidents.md`** — каждая намеренная поломка и каждый реальный инцидент. Учебный конспект и одновременно источник ответов на «расскажи про сложный баг».

## 8. AI-глава — v2, заложено на будущее

**В план недель 1–8 не входит.** Раздел зафиксирован, чтобы v2 не потребовала переписывания.

Что будет:

1. **Разбор брокерских отчётов через LLM** — PDF Сбера и любого нового брокера: LLM извлекает операции по строгой JSON-схеме → валидация Zod → тот же идемпотентный путь нормализации. LLM-парсер = ещё одна реализация `TradeSource`.
2. **Месячный дайджест по портфелю** — агрегаты из ClickHouse → LLM → доставка через `notifier` в Telegram.
3. **Заметки к сделкам + семантический поиск (RAG)** — «почему я это купил», pgvector в том же PostgreSQL (либо Qdrant).
4. **MCP-сервер над своим API** — ассистент отвечает на «сколько я потерял на альтах в этом году» через tool-calling к дневнику.

Крючки в v1 (иначе v2 дорожает):

- `raw_imports` хранит сырьё целиком — заложено в §4, LLM перегонит архив задним числом.
- Нормализация отделена от транспорта — заложено в §4.
- **`decisions` заводятся сразу, со 2-й недели** (§2.1) — тезисы, настроение, контекст. RAG и разборы без накопленного корпуса бесполезны; полгода записей превращают демку в работающую вещь.
- **Сборщик новостей запускается на 6-й неделе**, хотя сама фича — в роадмапе: RSS не отдаёт историю задним числом.

Дисциплина, зафиксированная заранее: ни одна финансовая запись не попадает в БД из LLM без подтверждения человеком (черновик «вот что я распознал»). Плюс минимальный набор evals — десяток отчётов с эталонной разметкой, чтобы менять промпт или модель не вслепую.

## Роадмап после v1

| Что | Требует ли переделки |
|---|---|
| Новостной фон в `context_snapshot` и в разборах | **нет.** Поле `jsonb`, снимок собирается одной точкой расширения — добавляется ключ `news`, миграция не нужна |
| AI-глава целиком (§8) | нет, крючки заложены в §2.1, §4 |
| GraphQL subscriptions вместо своего WebSocket | локальная замена транспорта на фронте |
| Qdrant вместо pgvector | замена адаптера |

**Оговорка по новостям.** Код переделывать не придётся, а вот **данные задним числом не восстановятся**: бесплатные RSS-ленты глубокой истории не отдают. Поэтому на 6-й неделе ставится не сама фича, а микро-сборщик: cron складывает ленты по своим тикерам в `news_items`, и всё. Отложить сборщик — единственное в этом роадмапе, что потом не догнать.

## Открытые вопросы

- Менять ли местами Т-Инвест и Bitget (российский портфель на 4-й неделе вместо 8-й, цена ≈ +3 дня).
- Когда снимать фича-флаг `exchange_keys` для посторонних пользователей.
- Порог значимости `n < 20` в поведенческих срезах — уточнить по факту, когда накопятся данные.
