# ADR-0001. Монорепозиторий на pnpm, а не репозиторий на сервис

**Дата:** 2026-10-19
**Статус:** принято

## Контекст

К концу плана в проекте пять приложений — `api`, `ingestor`, `core`, `notifier`, `web` — и два общих пакета: `contracts` с типами событий и денежными примитивами, `db` со схемой Prisma и миграциями.

Существенно вот что:

- **Типы событий общие для бэкенда и фронта.** Событие «сделка записана» публикует `core`, потребляют `notifier` и `web`. Схема события меняется чаще всего остального.
- **Денежный примитив один на всех.** `Money` из `contracts` используется и в доменном ядре, и в фикстурах, и в формах. Правило «`number` для денег запрещён везде» имеет смысл только если «везде» — одно место.
- **Разработчик один.** Накладные расходы на синхронизацию между репозиториями платит он же, и платит из тех девяти недель, которые отведены на обучение.
- **Одна ссылка для интервьюера.** Проект должен читаться за два прохода, а не собираться по трём адресам.

## Решение

Один репозиторий, pnpm workspaces: `apps/*` — приложения, `packages/*` — общий код. Версии зависимостей точные, без `^`, лок-файл коммитим.

Границы между сервисами проводятся **не стенками репозиториев, а владением данными**: каждый сервис ходит только в свою схему PostgreSQL, в чужие таблицы — через API или события.

## Отвергнутые варианты

**Репозиторий на сервис.** Изменение схемы события превращается в согласованную серию PR по нескольким репозиториям плюс публикация новой версии `contracts` в реестр. Для команды с несколькими владельцами это цена за независимые релизы; у соло-разработчика независимых релизов нет, а цена есть.

**Два репозитория, бэкенд и фронт.** Выглядит естественно, пока не задашь вопрос, где живут общие типы событий. Любой ответ — в одном из двух или в третьем пакете — кладёт шов ровно туда, где изменения идут чаще всего.

**Монорепозиторий с Nx или Turborepo.** Дают граф задач, кеш и выборочные сборки. На нашем масштабе полный прогон занимает секунды, а ещё один слой со своей ментальной моделью стоит дороже выигрыша. Тот же довод, по которому в ADR-0002 отклонён Panda CSS.

**Git submodules.** Классический неверный ответ: сложность распределённых репозиториев сохраняется целиком, атомарности изменений не появляется.

## Последствия

- `docker compose up` поднимает всю инфраструктуру, а `pnpm install` — все зависимости. Один вход для нового человека и для себя через месяц.
- Изменение схемы события — один коммит и один PR. Рассинхронизации версий `contracts` между сервисами не существует как класса проблем.
- **CI гоняет всё на любое изменение.** Пока прогон занимает секунды — это преимущество, а не недостаток. Когда начнёт мешать, в пайплайн добавится фильтрация по изменённым путям, а не второй репозиторий.
- **pnpm не поднимает зависимости в корень.** Пакет, не объявивший зависимость, её не увидит — на этом уже спотыкались дважды: тестовый харнесс не видел `@prisma/adapter-pg`, а затем сам `@thesis/db`, пока у `apps/api` не появился свой `package.json`. Побочная польза: забытая зависимость обнаруживается сразу, а не на чужой машине.
- **Сгенерированный клиент Prisma лежит в `packages/db/generated` и не коммитится.** Значит `pnpm db:generate` обязателен перед проверками — и локально после каждого изменения схемы, и первым шагом в CI. Без него не проходит даже typecheck.
- **Главный риск — размывание границ.** В одном репозитории ничто физически не мешает `notifier` залезть в таблицы `core`: импорт отработает, тесты пройдут. Стенку заменяет дисциплина, а дисциплина забывается. Противоядия два: отдельная схема PostgreSQL на сервис с правами на неё и явный запрет в AGENTS.md. Проверяется это в задаче 7 вместе с RLS.
- Второй риск мягче: монорепозиторий соблазняет тащить в одну ветку правки по всему репозиторию. Отсюда правило про одну задачу на ветку и дифф до ~300 строк — оно нужно именно здесь, а в репозитории на сервис соблюдалось бы само.
