## Postgres 18 не стартует с томом по старому пути

**Дата:** 14.10.2026 · **Задача:** 2 · **Потеря данных:** нет

`docker compose up -d --wait` вернул `container thesis-postgres-1 exited (1)`, redis при этом
поднялся и был `healthy`. В логах контейнера:

```
Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" ...
       Counter to that, there appears to be PostgreSQL data in:
         /var/lib/postgresql/data (unused mount/volume)
```

**Причина.** Образы `postgres:18+` поменяли раскладку: `PGDATA` теперь
`/var/lib/postgresql/18/docker`, а монтировать полагается `/var/lib/postgresql`. В
`compose.yml` стоял путь из эпохи 16/17 — `/var/lib/postgresql/data`. Образ видит там точку
монтирования, считает её неапгрейженной базой и отказывается стартовать, вместо того чтобы
молча поверх неё инициализироваться. Подкаталог с номером версии нужен, чтобы работал
`pg_upgrade --link` без пересечения точек монтирования.

**Лечение.** Том смонтирован в `/var/lib/postgresql`. Пересоздавать его не потребовалось:
`initdb` до падения не выполнялся, том был пуст.

**Выводы.**

1. Путь монтирования — часть контракта образа, а не деталь. Подъём мажорной версии может его
   сменить, и тогда старый конфиг не «работает чуть иначе», а не запускается вовсе.
2. `up -d --wait` отработал лучше голого `up -d`: тот вернул бы ноль и оставил мёртвый
   контейнер, а падение всплыло бы на следующей команде, вдали от причины.
3. Healthcheck здесь не помог и не мог: процесс не дожил до первой пробы. Healthcheck
   проверяет живой сервис, а не факт запуска.

## Prisma не находит корневой конфиг при запуске из пакета

**Дата:** 14.10.2026 · **Задача:** 3 · **Поймано до поломки**

В плане команды шага 2 были записаны как `pnpm --filter @thesis/db exec prisma migrate dev`.
Проверка тем же способом, но безопасным подкомандой:

```
$ pnpm exec prisma validate                        # из корня
Loaded Prisma config from prisma.config.ts.
Prisma schema loaded from packages/db/prisma/schema.prisma.

$ pnpm --filter @thesis/db exec prisma validate    # cwd = packages/db
Prisma schema loaded from prisma/schema.prisma.
```

**Причина.** `prisma.config.ts` ищется относительно текущего каталога, вверх по дереву CLI не
идёт. Из `packages/db` конфиг не подхватился, схему CLI нашёл по соглашению
(`prisma/schema.prisma`), и всё выглядело рабочим. Но в Prisma 7 адрес базы живёт **только** в
конфиге: в `datasource` его больше нет. То есть `migrate deploy` ушёл бы в пустой
`datasource.url`.

**Лечение.** Все вызовы CLI — из корня: скрипты `db:migrate` и `db:generate` в корневом
`package.json`, а в харнессе тестов `execFileSync` с `cwd: repoRoot`. Команда в плане
исправлена.

**Выводы.**

1. Сигналом была **отсутствующая** строка `Loaded Prisma config from ...`, а не ошибка. Самый
   дорогой класс поломок — тот, где инструмент не падает, а тихо берёт другой источник
   настроек.
2. Проверять такие вещи надо безопасной подкомандой (`validate`), а не той, что меняет
   состояние. Разница в выводе видна одинаково, цена ошибки — разная.

## Удаление базовой ветки закрыло соседний PR

**Дата:** 19.10.2026 · **Задача:** разбор ветки на пять PR · **Потеря данных:** нет

Пять задач лежали в одной ветке, разнесли их на стопку PR: каждый поверх предыдущего. Мерж
первого сделали одной командой вместе с удалением ветки:

```
$ gh pr merge 2 --squash --delete-branch
$ gh pr edit 3 --base main
GraphQL: Cannot change the base branch of a closed pull request. (updatePullRequest)
```

**Причина.** GitHub перенаправляет PR на `main`, когда его базовую ветку **мержат**, но
**закрывает** PR, когда базовую ветку **удаляют**. Флаг `--delete-branch` сделал второе в том
же вызове, что и первое, — и соседний PR закрылся, а у закрытого PR базу менять уже нельзя.

**Лечение.** Открыли замену — новый PR на ту же ветку. Дальше порядок стал такой: перенаправить
базу следующего PR на `main`, перебазировать его ветку, запушить, и только потом удалять
влитую. Остальные три прошли без потерь.

**Выводы.**

1. В стопке PR удаление ветки — отдельный последний шаг, а не часть мержа. `--delete-branch`
   выглядит безобидным удобством, а является изменением базы для всех, кто стоит сверху.
2. Сквош-мерж в стопке всегда требует ребейза следующей ветки: сквош создаёт коммит, которого
   нет в её истории, и дифф начинает показывать мнимые конфликты.
3. Цена ошибки — закрытый PR и сбитая нумерация в истории (2, 7, 4, 5, 6). Дёшево только
   потому, что заметили сразу.

## Живая проверка соврала: отвечал забытый процесс

**Дата:** 19.10.2026 · **Задача:** 4–5, доводка · **Потеря данных:** нет

Перевели health-пробу на `@nestjs/terminus` и сузили `Path` у refresh-cookie. Запустили
приложение, проверили curl — и получили **старое** поведение: `{"status":"ok","db":"up"}`
вместо формы терминуса и `Path=/auth` вместо `/auth/refresh`.

**Причина.** На порту 3000 висел dev-сервер с предыдущего запуска. Новый процесс умер с
`EADDRINUSE`, а curl ответил старый. Сбивало с толку то, что фоновая задача отрапортовала
«failed with exit code 1» — ровно так же выглядит процесс, который сам же и погасил.

**Как нашли.** Посмотрели, что лежит в `dist`: там были и терминус, и новый путь cookie, то
есть сборка свежая, а значит отвечает не она. Дальше `grep EADDRINUSE` в логе фоновой задачи.

**Выводы.**

1. Живая проверка — доказательство только если известно, **какой процесс** ответил. Перед
   доверием к curl надо смотреть, кто слушает порт.
2. Упавший на занятом порту сервер и остановленный вручную выглядят в выводе одинаково.
   Отличать их по коду выхода нельзя — только по логу.
3. Это второй случай за день, когда проверка была зелёной и ничего не проверяла (первый —
   гоночный тест, который проходил на наивной реализации). Общее у них одно: зелёный результат
   сам по себе не говорит, что проверено то, что думаешь.

## Забытый withUser вёл себя по-разному в зависимости от соединения

**Дата:** 20.10.2026 · **Задача:** 7 · **Поймано до поломки**

Шаг 6 задачи 7 требует убрать `true` из `set_config` и посмотреть на утечку. Убрали —
утечка на месте: запрос, в котором `withUser` не вызывался вообще, вернул сделку чужого
пользователя, а `app.user_id` на соединении после коммита держал его идентификатор.
Вернули `true`, прогнали тот же зонд ожидая ноль строк — и получили
`ERROR: invalid input syntax for type uuid: ""`.

**Причина.** `SET LOCAL` по завершении транзакции не удаляет кастомную переменную, а
восстанавливает прежнее значение — а для параметра, которого до этого не существовало, это
**пустая строка**, не «отсутствует». Поэтому `current_setting('app.user_id', true)` отдаёт
`''`, и `''::uuid` падает. На соединении, которое `withUser` ещё не обслуживало, параметра
действительно нет, функция отдаёт NULL и запрос возвращает ноль строк. Один и тот же забытый
`withUser` давал пустой список или ошибку в зависимости от того, какое соединение выдал пул.

**Лечение.** Убрали `missing_ok`: политики перешли на `current_setting('app.user_id')::uuid`
миграцией `20261020115532_rls_require_user_id`. Теперь это всегда ошибка —
`unrecognized configuration parameter` на свежем соединении и `invalid input syntax for type
uuid: ""` на переиспользованном. Забытый `withUser` — баг в коде, а не анонимный запрос, и
падать он должен сразу.

**Выводы.**

1. Третий аргумент `set_config` — не оптимизация. Без него значение остаётся на соединении,
   уезжает через пул к следующему запросу, и чужие данные видны тому, кто ничего не выставлял.
   На одиночном запросе это не видно совсем, нужен второй запрос по тому же соединению.
2. `current_setting(name, true)` читается как «нет значения — вернёт NULL», но это верно
   только пока параметр ни разу не ставили в этой сессии. После `SET LOCAL` он остаётся со
   значением `''`. Выбор между «ноль строк» и «ошибка» требует это знать.
3. Тест изоляции такого не поймает: он делает запросы только внутри `withUser`, то есть
   проверяет исключительно правильный путь. Тест, покрывающий только корректный вызов,
   ничего не говорит о забытом.

## Позиция вне транзакции: сделка есть, позиции нет

**Дата:** 20.10.2026 · **Задача:** 9 · **Поймано до поломки**

Шаг 6 задачи 9 требует вынести обновление позиции за пределы транзакции и посмотреть на
рассогласование. Вынесли, прогнали покупку двух штук со сбоем между записью сделки и
обновлением позиции. В базе осталось: **сделок 1, лотов 1, позиций 0.** Лот утверждает, что
открыто две штуки, а позиции по инструменту не существует вовсе — инвариант «сумма остатков
лотов равна позиции» нарушен, и восстановить его можно только пересчётом по сделкам.

**Причина.** Запись состояла из трёх частей — сделка, лот, позиция, — и только первые две
были под одной транзакцией. Любой сбой в промежутке фиксирует половину работы. Сбой здесь не
выдуманный: `consumeFifo` бросает `not enough quantity` уже после вставки сделки, а в проде к
этому добавятся таймаут соединения и перезапуск процесса.

**Как нашли.** Первый зонд был неверный: я вынес обновление позиции, но оставил ему тот же
объект транзакции, и Prisma отказала — `Transaction already closed: A query cannot be executed
on a committed transaction`. Это не рассогласование данных, а защита клиента. Чтобы увидеть
настоящую поломку, обновление пришлось отправлять в **новую** транзакцию.

**Лечение.** Ничего не меняли: сервис с самого начала пишет всё внутри одного `withUser`.
Вместо записи инцидента в код добавлен постоянный тест «неудачная продажа не оставляет ни
сделки, ни изменения позиции» — он проверяет откат на том самом естественном сбое.

**Выводы.**

1. Транзакция здесь не про скорость и не про блокировки, а про инвариант: позиция — это
   агрегат лотов, и жить порознь они не могут даже на миллисекунду.
2. Prisma не даёт переиспользовать закрытую транзакцию, и это стоит знать: наивная попытка
   «дописать позже» падает с внятной ошибкой, а не портит данные молча. Испортить данные
   получается только сознательно — отдельной транзакцией.
3. Третий случай за два дня, когда проверка зелёная и ничего не проверяет: зонд, который
   падает не по той причине, что задумано, доказывает не больше, чем зелёный тест. Смотреть
   надо не на «упало», а на **текст** падения.

## Стопка PR рассыпалась от сквош-мержа

**Дата:** 21.10.2026 · **Задача:** разбор накопленного дерева на пять PR · **Потеря данных:** нет

Накопилось пять несвязанных работ в одном дереве. Разнёс по веткам стопкой — каждая следующая
от предыдущей, PR в базу предыдущего, — и собирался мержить по порядку. Первый прошёл. На
втором `gh pr merge` вернул подсказку «сначала смержи main в ветку» вместо успеха, я вывод не
прочитал и удалил его ветку. PR закрылся.

**Причина.** Сквош-мерж родителя кладёт в `main` **новый** коммит вместо исходного. Дочерняя
ветка стоит на исходном, и git видит два разных изменения одних и тех же строк — конфликт.
Стопка PR работает с обычным мержем и ломается от сквоша, а сквош у нас обязателен по
`AGENTS.md`.

Вторая ошибка в той же серии: смержив третий PR, я удалил его ветку, не проверив, что она
**база** для четвёртого. Удаление базовой ветки закрывает дочерний PR — это уже записано выше,
записью «Удаление базовой ветки закрыло соседний PR», и я эту запись цитировал за час до того,
как повторил.

**Лечение.** Оба PR пересозданы от свежего `main`. Дальше — без стопки: по одной ветке,
`git rebase origin/main`, при конфликте с уже смерженным коммитом `git rebase --skip`. Три
оставшихся PR прошли без единого конфликта.

**Выводы.**

1. Сквош-мерж и стопка PR несовместимы. Либо обычный мерж и стопка, либо сквош и по одной
   ветке за раз. Третьего нет.
2. `gh pr merge` при отказе печатает подсказку и возвращает ноль. Проверять надо **состояние
   PR**, а не вывод команды: `gh pr view N --json state`.
3. Перед удалением любой ветки — убедиться, что она не база открытого PR. Знать правило
   недостаточно: я его знал, пересказывал вслух и всё равно нарушил через час. Помогает не
   память, а проверка перед действием.

## Шаг «сломать специально» сломал не то, что я собирался ломать

**Дата:** 21.10.2026 · **Задача 16**

По плану шаг 5 выглядел так: заменить `ON CONFLICT DO NOTHING` на «сначала `SELECT`, потом
`INSERT`», запустить два импорта одного отчёта параллельно и увидеть задвоенные сделки.

Заменил, запустил — и **дублей не появилось**. Вместо них одна из двух попыток отвалилась, но
не на вставке сделки, а на создании инструмента:

```
отказ: Invalid `this.prisma.instrument.upsert()` invocation
```

Два вывода, и второй важнее первого.

**Первый: дубли защищает индекс, а не `ON CONFLICT`.** Уникальный индекс
`(account_id, provider, external_id)` стоит в базе с задачи 7. Пока он есть, наивная проверка
«нет ли такой строки» не приводит к дублям — она приводит к падению импорта на нарушении
уникальности. Разница между наивным кодом и правильным не в том, появятся ли дубли, а в том,
отличает ли код штатную повторную заливку от аварии. Чтобы увидеть настоящие дубли, пришлось бы
снести индекс — то есть сломать не сервис, а схему.

**Второй: нашлась настоящая гонка, и в моём же коде.** `InstrumentsService.create` был написан
в задаче 13b через `prisma.instrument.upsert` с комментарием, что это защита как раз от
одновременного добавления одного тикера. Защитой он не был: Prisma разворачивает такой `upsert`
в чтение и запись двумя запросами, и два импорта, резолвящие `SBER` одновременно, ловят
нарушение уникальности. Воспроизвелось три раза из трёх — редкий случай, когда гоночный тест в
этом проекте действительно создаёт контенцию (сравни с записью «Гоночные тесты через сервис не
создают контенции» в `docs/unknowns.md`).

**Лечение.** `upsert` заменён на `insert … on conflict (symbol, class) do nothing` с чтением
после вставки. Гоночный тест оставлен в `apply-import.int.test.ts`: обе попытки обязаны
завершиться, одна создаёт девять операций, вторая пропускает девять, сделок в базе четыре.

**Вывод.** Комментарий «через upsert, а не найти-и-создать: иначе гонка» был написан про
намерение, а не про поведение библиотеки, и прожил две задачи, пока его не проверили
параллельным запуском. Комментарий, объясняющий защиту, стоит писать только после теста,
который эту защиту ломает.


## Решение задним числом не привязывалось ни к чему

**22.10.2026.** На экране «Сделки без тезиса» есть ссылка «записать задним числом»: она открывает
форму решения с подставленным счётом, бумагой и стороной. Человек записал решения по конкретным
сделкам — и сделки остались висеть без тезиса.

Две причины, обе в нашем коде:

1. Форма передавала счёт, бумагу и сторону, но **не сделку**. Привязать её было нечем:
   автопривязка (`matchDecisionToTrades`) требует, чтобы сделка была **позже** решения — это
   правило из `design.md` §2.1 против рационализации задним числом, и оно верно. Для решения
   задним числом оно означает «не привяжется никогда».
2. Экран разметки исключал решения с `post_factum` из списка подходящих
   (`suitable(): … && !decision.postFactum`). То есть предлагал записать такое решение и тут же
   отказывался его предлагать для привязки.

Вместе это давало замкнутый круг: единственный честный способ разметить импортированную сделку не
работал ни автоматически, ни руками.

**Починено:** `tradeId` уезжает в форму и в `POST /decisions` полем `tradeIds`, создание решения
привязывает названные сделки само (окно горизонта к ним не применяется — честность держит пометка
`post_factum`, а не отказ привязать); фильтр `!postFactum` из списка подходящих убран, а в списке
теперь видно, какое решение записано задним числом.

**Чему учит:** правило «сделка должна быть позже решения» верно для автопривязки и бессмысленно
для ручной. Когда одно правило обслуживает два разных пути, второй путь обычно оказывается
сломан — и ломается он молча, потому что «ноль привязок» выглядит как «нечего привязывать».


## Правка скрипта ломает его же монтирование в контейнер

**22.10.2026.** `pnpm db:role` перестал работать сразу после того, как в
`docker/postgres/init-app-role.sh` добавилась роль воркера:

```
sh: can't open '/docker-entrypoint-initdb.d/init-app-role.sh': No such file or directory
```

Файл на месте, монтирование в `docker inspect` тоже на месте и указывает ровно на него. Причина в
том, что bind-mount **одиночного файла** привязывается к inode, а не к пути: редактор (и любой
инструмент, который пишет во временный файл и переименовывает его) создаёт новый inode, и внутри
контейнера монтирование указывает на исчезнувший старый.

**Обход на один раз:** прогнать скрипт через stdin —
`docker compose exec -T postgres sh -s < docker/postgres/init-app-role.sh`.
**Лечение:** пересоздать контейнер (`docker compose up -d postgres`), тогда монтирование
привязывается к новому inode.

**Чему учит:** монтировать каталог, а не файл, если файл будут править. Сейчас каталог
`docker-entrypoint-initdb.d` и монтируется по файлу намеренно (чтобы в initdb.d не попало лишнее),
так что цена известна: после каждой правки скрипта — пересоздание контейнера базы.


## `prisma migrate dev` повис и заблокировал сам себя

**22.10.2026.** Прогон `pnpm db:migrate` не завершился за десять минут, второй прогон молчал. Три
причины наложились:

1. **Вывод прятал `tail`.** Команда шла как `pnpm db:migrate | tail -3`, а `tail` буферизует до
   конца команды — поэтому не было видно, что Prisma задаёт вопрос. Вопрос был такой: «Enter a name
   for the new migration». Она хотела **ещё одну** миграцию, потому что имя первичного ключа в
   моей написанной руками миграции (`provider_prices_pkey`) не совпало с тем, что она выводит из
   имени таблицы (`instrument_prices_pkey`).
2. **Процесс не умер вместе с оболочкой.** Остановка фоновой задачи убила `pnpm`, но `prisma` и
   её schema-engine остались жить и держали **advisory-блокировку** миграций. Второй прогон ждал
   её молча — ровно тот же механизм, который в задаче 17 защищает импорт от двойного применения.
3. **Правка применённой миграции сбила контрольную сумму.** Исправив имя ключа в файле, я получил
   «The migration was modified after it was applied» и предложение сбросить базу — а в ней живой
   импорт и шесть тысяч цен.

**Как вышел:** убил зависшие процессы (`pkill -f "prisma/build/index.js migrate dev"`, схема-движок
отдельно), переименовал ограничение в живой базе (`alter table … rename constraint`), пересчитал
контрольную сумму файла (`shasum -a 256`) и обновил её в `_prisma_migrations`. После этого
`migrate dev` ответил «Already in sync».

**Чему учит:** не прогонять интерактивные команды через `tail`; после правки применённой миграции
чинить и файл, и запись о нём; «сбросить базу» — всегда первое предложение Prisma и почти никогда
правильное.

## Скрипт ролей уронил все интеграционные тесты

**22.10.2026.** После добавления роли воркера четырнадцать файлов интеграционных тестов перестали
запускаться: `Health check failed: unhealthy` — контейнер PostgreSQL не поднимался вовсе.

Причина: в `init-app-role.sh` появился безусловный `grant select on table public.instruments`. На
свежем кластере скрипт выполняется из `initdb.d`, то есть **до** миграций, — справочника ещё нет,
`ON_ERROR_STOP=1` валит скрипт, entrypoint считает инициализацию неудачной. В рабочей базе это не
проявилось: там таблица существовала.

**Лечение:** грант под условием существования таблицы, а постоянное право выдаёт миграция.
**Чему учит:** всё, что выполняется из `initdb.d`, обязано работать на пустой базе — там нет ни
одной таблицы приложения, и порядок «сначала роли, потом схема» не изменить.
