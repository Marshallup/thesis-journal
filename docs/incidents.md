## Postgres 18 не стартует с томом по старому пути

**Дата:** 14.10.2026 · **Задача:** 2 · **Потеря данных:** нет

`docker compose up -d --wait` вернул `container thesis-postgres-1 exited (1)`, redis при этом
поднялся и был `healthy`. В логах контейнера:

```
Error: in 18+, these Docker images are configured to store database data in a
       format which is compatible with "pg_ctlcluster" ...
       Counter to that, there appears to be PostgreSQL data in:
         /var/lib/postgresql/data (unused mount/volume)
```

**Причина.** Образы `postgres:18+` поменяли раскладку: `PGDATA` теперь
`/var/lib/postgresql/18/docker`, а монтировать полагается `/var/lib/postgresql`. В
`compose.yml` стоял путь из эпохи 16/17 — `/var/lib/postgresql/data`. Образ видит там точку
монтирования, считает её неапгрейженной базой и отказывается стартовать, вместо того чтобы
молча поверх неё инициализироваться. Подкаталог с номером версии нужен, чтобы работал
`pg_upgrade --link` без пересечения точек монтирования.

**Лечение.** Том смонтирован в `/var/lib/postgresql`. Пересоздавать его не потребовалось:
`initdb` до падения не выполнялся, том был пуст.

**Выводы.**

1. Путь монтирования — часть контракта образа, а не деталь. Подъём мажорной версии может его
   сменить, и тогда старый конфиг не «работает чуть иначе», а не запускается вовсе.
2. `up -d --wait` отработал лучше голого `up -d`: тот вернул бы ноль и оставил мёртвый
   контейнер, а падение всплыло бы на следующей команде, вдали от причины.
3. Healthcheck здесь не помог и не мог: процесс не дожил до первой пробы. Healthcheck
   проверяет живой сервис, а не факт запуска.

## Prisma не находит корневой конфиг при запуске из пакета

**Дата:** 14.10.2026 · **Задача:** 3 · **Поймано до поломки**

В плане команды шага 2 были записаны как `pnpm --filter @thesis/db exec prisma migrate dev`.
Проверка тем же способом, но безопасным подкомандой:

```
$ pnpm exec prisma validate                        # из корня
Loaded Prisma config from prisma.config.ts.
Prisma schema loaded from packages/db/prisma/schema.prisma.

$ pnpm --filter @thesis/db exec prisma validate    # cwd = packages/db
Prisma schema loaded from prisma/schema.prisma.
```

**Причина.** `prisma.config.ts` ищется относительно текущего каталога, вверх по дереву CLI не
идёт. Из `packages/db` конфиг не подхватился, схему CLI нашёл по соглашению
(`prisma/schema.prisma`), и всё выглядело рабочим. Но в Prisma 7 адрес базы живёт **только** в
конфиге: в `datasource` его больше нет. То есть `migrate deploy` ушёл бы в пустой
`datasource.url`.

**Лечение.** Все вызовы CLI — из корня: скрипты `db:migrate` и `db:generate` в корневом
`package.json`, а в харнессе тестов `execFileSync` с `cwd: repoRoot`. Команда в плане
исправлена.

**Выводы.**

1. Сигналом была **отсутствующая** строка `Loaded Prisma config from ...`, а не ошибка. Самый
   дорогой класс поломок — тот, где инструмент не падает, а тихо берёт другой источник
   настроек.
2. Проверять такие вещи надо безопасной подкомандой (`validate`), а не той, что меняет
   состояние. Разница в выводе видна одинаково, цена ошибки — разная.
