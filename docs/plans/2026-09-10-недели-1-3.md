## Глобальные ограничения

- **Деньги — только `numeric` в БД и `decimal.js` в коде.** `number` для денег и количеств запрещён везде, включая тесты и фикстуры. Точность: `numeric(38,18)` для количеств, `numeric(28,8)` для цен и сумм.
- **Все времена — `timestamptz`, хранение в UTC.** Отображение в MSK делает фронт.
- **Код, имена и коммиты — на английском** (репозиторий публичный, его читают интервьюеры). Документация в `docs/` — на русском.
- **SQL пишет человек.** Миграции, запросы, политики RLS, триггеры — слой 🖐 из §7.1 спеки.
- **Тесты пишет человек.** ИИ может предложить реализацию под уже написанный тест.
- Живые внешние API из тестов не дёргаются — только фикстуры.
- Секреты не в репозитории: файл окружения в `.gitignore`, шаблон `*.example` с пустыми значениями — в репозитории.
- Задача ≤ 4 часов и ≤ ~300 строк диффа. Каждая заканчивается зелёными тестами и запускающимся приложением.
- Каждая задача = ветка `task/NN-<slug>` = PR в свой же репозиторий с описанием и вопросом «что бы спросили на собеседовании по этому коду».

- [x] **Шаг 4: Минимальная реализация**

`packages/contracts/src/money.ts`:

> Импорт **именованный**, не дефолтный. В `decimal.d.ts` под именем `Decimal` слиты класс, функция и namespace, и `export default` подхватывает сигнатуру без конструктора: `import Decimal from 'decimal.js'` падает с `TS2351: This expression is not constructable`. Проверено на нашем tsconfig (`module: nodenext`, ESM-пакет).

```ts
import { Decimal } from 'decimal.js'

// An isolated constructor rather than Decimal.set: the configuration stays
// inside Money. Decimal.set mutates the library globally, so any other code in
// the process would inherit our precision, and its own Decimal.set would break
// our toString().
const D = Decimal.clone({ precision: 40, toExpNeg: -30, toExpPos: 40 })

export class Money {
  readonly #value: Decimal

  private constructor(value: Decimal) {
    this.#value = value
  }

  static of(value: string | Money): Money {
    if (typeof value !== 'string' && !(value instanceof Money)) {
      throw new TypeError('number is not allowed for money, use string')
    }
    return value instanceof Money ? value : new Money(new D(value))
  }

  plus(x: string | Money): Money {
    return new Money(this.#value.plus(Money.of(x).#value))
  }
  minus(x: string | Money): Money {
    return new Money(this.#value.minus(Money.of(x).#value))
  }
  times(x: string | Money): Money {
    return new Money(this.#value.times(Money.of(x).#value))
  }
  eq(x: string | Money): boolean {
    return this.#value.eq(Money.of(x).#value)
  }
  lt(x: string | Money): boolean {
    return this.#value.lt(Money.of(x).#value)
  }
  gte(x: string | Money): boolean {
    return this.#value.gte(Money.of(x).#value)
  }
  isNegative(): boolean {
    return this.#value.isNegative()
  }
  toString(): string {
    return this.#value.toFixed()
  }
}
```

```ts
import { execFileSync } from 'node:child_process'
import { resolve } from 'node:path'
import { PostgreSqlContainer } from '@testcontainers/postgresql'
import { PrismaClient, PrismaPg } from '@thesis/db'

const repoRoot = resolve(import.meta.dirname, '../../..')

export async function withTestDb() {
  const container = await new PostgreSqlContainer('postgres:18-alpine').start()
  const url = container.getConnectionUri()

  // Из корня, иначе CLI не найдёт prisma.config.ts. DATABASE_URL здесь
  // перебивает рабочий файл: dotenv не переписывает уже заданные переменные.

    cwd: repoRoot,
    env: { ...process.env, DATABASE_URL: url },
    stdio: 'inherit',
  })

  const prisma = new PrismaClient({ adapter: new PrismaPg({ connectionString: url }) })

  return {
    prisma,
    url,
    stop: async () => {
      await prisma.$disconnect()
      await container.stop()
    },
  }
}
```

**Область задачи сознательно сужена.** Ротация здесь одноразовая: применённый refresh
списывается, выдаётся новый. Обнаружения кражи токена — семейств, детектора повторного
использования, отзыва цепочки — в этой задаче **нет**. Цель «защититься от кражи
refresh-токена» зафиксирована в `docs/unknowns.md` вместе с разобранными вариантами;
реализация — отдельной задачей, когда будет выбран способ отличать кражу от обычного

- [x] **Шаг 1: Написать падающие тесты на ротацию** 🖐

Главный тест этой задачи — одноразовость refresh: применённый токен больше не работает,
а выданный ему на замену работает.

`apps/api/test/auth.e2e.test.ts`:

```ts
it('не принимает refresh-токен повторно', async () => {
  const agent = request.agent(app.getHttpServer())
  const email = 'rotate@b.c'

  const registered = await agent.post('/auth/register').send({ email, password: PASSWORD })
  expect(registered.status).toBe(201)

  const login = await agent.post('/auth/login').send({ email, password: PASSWORD })
  expect(login.status).toBe(200)

  const first = refreshCookie(login)

  // агент обновился — токен провернулся, cookie заменилась
  const rotated = await agent.post('/auth/refresh')
  expect(rotated.status).toBe(200)

  // старая cookie больше не принимается
  const replay = await request(app.getHttpServer()).post('/auth/refresh').set('Cookie', first)
  expect(replay.status).toBe(401)

  // а у легитимного клиента сессия жива: отзыва цепочки в этой задаче нет
  const again = await agent.post('/auth/refresh')
  expect(again.status).toBe(200)
})
```

Последняя проверка фиксирует именно то, что мы сознательно **не** делаем: отказ вору не
выбрасывает честного клиента. Когда появится обнаружение кражи, этот тест изменится, и
изменится осознанно.

Второй обязательный тест — **гоночный**: два запроса с одним refresh одновременно.

```ts
it('при двух одновременных refresh проворачивается ровно один', async () => {
  const agent = request.agent(app.getHttpServer())
  await agent.post('/auth/register').send({ email: 'race@b.c', password: 'correct horse battery' })
  const login = await agent.post('/auth/login').send({ email: 'race@b.c', password: 'correct horse battery' })
  const cookie = login.headers['set-cookie']

  const results = await Promise.all(
    Array.from({ length: 8 }, () =>
      request(app.getHttpServer()).post('/auth/refresh').set('Cookie', cookie),
    ),
  )

  expect(results.filter((r) => r.status === 200)).toHaveLength(1)

  // и сессия после гонки жива: проигравшие не должны ничего ломать
  const winner = results.find((r) => r.status === 200)
  const next = await request(app.getHttpServer())
    .post('/auth/refresh')
    .set('Cookie', refreshCookie(winner))
  expect(next.status).toBe(200)
})
```

Важная оговорка про зубы этого теста. `.claude/rules/tests.md` требует, чтобы гоночный тест
падал на наивной реализации. Проверено подменой: на «прочитать, потом удалить» он **не**
падает, потому что эта реализация не сломана — блокировка строки и так пропускает одного.
Тест фиксирует инвариант «один токен — одна ротация», но двух корректных вариантов между
собой не различает. На `UPDATE`-варианте из первой редакции плана он бы упал.

Ещё одно наблюдение из той же проверки: восемь запросов через supertest **не создают
гонку** — они сериализуются, и проигравшие просто не находят токен (при подмене было видно
`200 401 401 401 401 401 401 401`, а не ошибки конкуренции). Поэтому тест зовёт сервис
напрямую: контенция нужна внутри Postgres, а не на уровне HTTP.

Третий тест — на регистр email, то самое отложенное решение из задачи 3: регистрация
приводит адрес к нижнему регистру, поэтому `A@B.C` после `a@b.c` должна получить 409,
а не создать второй аккаунт.

```prisma

  id        String   @id @default(dbgenerated("uuidv7()")) @db.Uuid
```

- [x] **Шаг 4: Реализация**

`apps/api/src/auth/auth.service.ts` — ключевая часть, остальное (контроллер, DTO, модуль) обычная обвязка Nest:

```ts
async rotate(rawToken: string) {
  const tokenHash = sha256(rawToken)

  return this.prisma.$transaction(async (tx) => {
    // Проверка и списание — одной операцией: DELETE … RETURNING. Параллельный
    // запрос с тем же токеном строки не найдёт и получит 401.
    const consumed = await tx.refreshToken.delete({ where: { tokenHash } }).catch((error: unknown) => {
      if (isRecordNotFound(error)) return null   // P2025: токен неизвестен или уже применён
      throw error
    })

    if (!consumed || consumed.expiresAt < new Date()) throw new UnauthorizedException()

    return this.issue(consumed.userId, tx)
  })
}
```

**Почему одной операцией.** Условие должно быть внутри изменяющего запроса, а не проверено
до него — жёсткое правило 3 в AGENTS.md и `.claude/rules/sql.md`. Тонкость в том, что у
`DELETE` условие попадает туда неявно: строка должна ещё существовать. Второй запрос
перечитывает её под блокировкой, не находит и затрагивает 0 строк. Поэтому даже наивное
«прочитать, потом удалить» здесь даёт ровно одного победителя — проверено подменой
реализации, тест не изменился.

Настоящая гонка была в первой редакции этого плана, где списание делалось через
`UPDATE … SET used_at = now() WHERE id = $1`. Условие `id = $1` после блокировки
по-прежнему истинно, поэтому второй запрос спокойно обновляет строку повторно, и **оба**
клиента проворачивают токен. Спасало бы только `WHERE used_at IS NULL` — то есть условие
внутри запроса, а не перед ним. Вывод не «одна операция вместо двух», а «условие в WHERE
изменяющего запроса».

Одна операция всё равно лучше двух: один круг до базы вместо двух и честная семантика
ошибок. `delete` по уникальному `token_hash` компилируется в `DELETE … RETURNING` — строку
забирает ровно один запрос, остальные получают P2025, который мы превращаем в 401. В
наивном варианте тот же P2025 прилетел бы необработанным и стал бы 500.

Ошибку надо разбирать по коду, а не глотать всё подряд: `isRecordNotFound` — маленький
guard на `error.code === 'P2025'`. Иначе обрыв соединения с базой приедет клиенту как 401,
то есть «разлогинься», вместо честной 500.

Применённый токен из таблицы исчезает — отдельного `usedAt` не нужно, а повторное
предъявление честно даёт 401. Чего здесь нет: отзыва остальных токенов этой сессии.
Проигравший в гонке или вор получают отказ лично, сессия живёт. Это сознательное решение,
записанное в `docs/unknowns.md`.

Пароли — `argon2.hash(password, { type: argon2id })`. Сам refresh-токен хешируется
обычным `sha256`: это случайная строка высокой энтропии, медленный KDF ей не нужен — он
защищает от перебора слабых паролей, а здесь перебирать нечего.

**Регистрация приводит email к нижнему регистру** — решение из задачи 3. В БД защиты нет
(проверено тестом в `packages/db/test/users.int.test.ts`), поэтому единственное место, где
это делается, — путь регистрации, и сравнение при логине должно идти по тому же
нормализованному значению.

**Зависимости**, которых нет в списке файлов: `argon2` для паролей, `@nestjs/jwt` для
подписи access-токенов, `@nestjs/passport` с `passport-jwt` под `jwt.strategy.ts`.
Версии и причины назвать до установки.

Реализацию писать руками: пройти лоты в порядке `(openedAt, id)`, откусывать от каждого, пока не наберётся `sellQty`, комиссию вычитать из суммарного результата пропорционально или целиком из первой консумации — решение принять и записать в `docs/learning.md` вместе с обоснованием.

**Про второй ключ сортировки.** Одного `openedAt` недостаточно: у сделок, приехавших из отчёта Сбера, время берётся из даты (задача 15), поэтому все сделки одного дня имеют одинаковый `executedAt`, а значит и лоты — одинаковый `openedAt`. `order by opened_at` без второго ключа даёт в PostgreSQL неопределённый порядок, и реализованный P&L начинает отличаться между прогонами на одних и тех же данных. **Обязательный тест:** два лота с одинаковым `openedAt` и разными ценами, продажа на объём одного лота. Результат должен быть один и тот же при любом порядке лотов во входном массиве. Property-based тест этого не поймает — там `openedAt` раздаются все разные.

## Задача 16. Идемпотентная запись операций

> **Решено до начала, 21.10.2026.** Три утверждения этой задачи — «потребляет

> ли куда сообщать о частичном успехе; если есть — незнакомую строку правильнее возвращать в
> отчёте об импорте, а не превращать в исключение. Записи в `docs/unknowns.md`: «Словарь операций

## Задача 18e. Имя счёта

> **Появилась по ходу 18b, 21.10.2026.** На экране импорта в списке счетов оказались два
> одинаковых пункта «sber»: подпись показывала только провайдера, а у человека два брокерских
> счёта у одного брокера — обычное дело. Первой правкой я дописал в подпись валюту, признак ИИС,
> дату и хвост идентификатора — и это был костыль: `#00d2` ничего человеку не говорит, он говорит,
> что показывать нечего. Настоящая причина — **у счёта нет имени**.

**Файлы:**
- Изменить: `packages/db/prisma/schema.prisma` + миграция `account_name`
- Изменить: `apps/api/src/accounts/{dto,accounts.service}.ts`
- Изменить: `apps/web/src/pages/accounts/new/account-form.tsx`, `apps/web/src/shared/ui/account-label.ts`
- Тест: `apps/api/test/manual-entry.int.test.ts`

- [x] **Шаг 1: Поле и миграция**

`name` необязательное: счёт часто заводят по ходу записи сделки, и требовать там название —
значит мешать. Уникальность — `(user_id, name)`: два счёта с одним именем у одного человека это
опечатка, а не выбор, а NULL-ы в индексе различны, поэтому безымянных может быть сколько угодно.
Повтор имени отдаёт 409 с внятным текстом, как регистрация по занятому email.

Миграция написана руками: `prisma migrate dev` на добавлении уникального индекса требует

Поле «Название, необязательно» с подсказкой. Подпись в списках берёт имя, если оно есть, и
только для безымянных остаётся прежняя схема: провайдер, валюта, ИИС, дата, хвост
идентификатора. То есть костыль не выброшен, а задвинут туда, где он честен — к счетам,
заведённым до появления поля и не названным до сих пор.
