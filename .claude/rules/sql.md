# SQL и миграции

**Этот слой пишет человек.** Твоя роль — объяснить, найти ошибку, предложить план. Если я прошу написать SQL за меня, переспроси один раз, и только потом делай.

## Миграции

- Схема правится в `schema.prisma`, миграция генерируется, **сгенерированный SQL читается целиком** перед применением.
- Партиции, триггеры, политики RLS, функции на PL/pgSQL пишутся руками в пустой миграции (`prisma migrate dev --create-only`).
- `prisma migrate dev` в Prisma 7 не запускает `prisma generate` — генерировать отдельно.
- Схема без простоя: expand → двойная запись → перелив → чтение из нового → contract. Ронять таблицу и создавать заново нельзя даже на учебном проекте: там реальные сделки.
- Миграции неизменяемы после применения на проде. Ошибся — новая миграция сверху.

## Типы

- Деньги: `numeric(28,8)`. Количества: `numeric(38,18)`. `float`, `double precision`, `money` — запрещены.
- Время: `timestamptz`. `timestamp` без зоны не использовать.
- Идентификаторы: `uuid`.

## Конкурентность

- Проверка и изменение — одной операцией: `UPDATE … WHERE amount >= $1 RETURNING`, а не «прочитать, сравнить, записать».
- Вставки, которые могут повториться, — через `ON CONFLICT` с явным уникальным индексом.
- Очередь на PostgreSQL — `FOR UPDATE SKIP LOCKED`.
- Защита от параллельного запуска процесса — `pg_try_advisory_xact_lock` (транзакционный, снимается сам).
- Инварианты — в БД (`CHECK`, `UNIQUE`, `FOREIGN KEY`), а не только в коде: сервисов четыре, база одна.

## Изоляция

- Приложение ходит под ролью без `BYPASSRLS`. Владелец таблицы обходит RLS — на этом легко обмануться при проверке.
- `set_config('app.user_id', …, true)` — третий аргумент `true` обязателен: иначе значение утечёт в следующий запрос из пула.

## Производительность

- Любой новый запрос по таблице свыше миллиона строк проверяется через `EXPLAIN ANALYZE` на настоящем объёме, а не на пустой базе.
- Удаление старых данных — `DETACH PARTITION` + `DROP`, не `DELETE`.
